## 1. Inspect the bootstrap

Require these existing paths:

```text
package.json
pnpm-workspace.yaml
client/package.json
server/package.json
.agents/skills/sk-start-next-hono/SKILL.md
```

If any are missing, stop and tell the user to create the base project first:

```powershell
npx sb-kit create next-hono <project-name>
```

Read the root and child manifests, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `.prettierrc.json`, `.prettierignore`, root `AGENTS.md`, and generated entry points. A non-empty matching workspace is expected. Preserve the generated applications and do not rerun create-next-app or create-hono.

Confirm only one root pnpm lockfile exists. Report child npm, Yarn, or Bun lockfiles instead of silently changing unrelated user files before approval.

## 2. Confirm current tooling

Use the versions already selected by the generated manifests and lockfile. Consult current official documentation only when version-sensitive behavior affects the approved setup.

Confirm whether authentication and Cloudflare R2 are required. PostgreSQL with Drizzle is the default data layer; authentication defaults to an admin/user boundary; R2 defaults to omitted.

Use the root scripts already generated by the CLI:

```json
{
  "scripts": {
    "dev:client": "pnpm --dir client dev",
    "dev:server": "pnpm --dir server dev",
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

Do not add sb-kit as a dependency or rerun its installer.

## 3. Configure the server

Reuse the valid scripts and dependencies created by the Hono Node.js template. Add only missing baseline dependencies:

```powershell
pnpm --dir server add drizzle-orm postgres zod
pnpm --dir server add -D drizzle-kit
```

Use `zod` or an existing validated-schema dependency; never add two validation libraries.

Keep one development command and one production entry point. Add only missing scripts supported by the generated toolchain:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate"
  }
}
```

Compose `server/src/index.ts` to:

- use `@hono/node-server`;
- use port `3001` by default;
- mount API routes beneath `/v1`;
- expose `GET /v1/health`;
- allow the exact `DASHBOARD_ORIGIN` in CORS;
- apply structured request logging and secure headers;
- use a global error handler;
- close the HTTP server on `SIGINT` and `SIGTERM`.

## 4. Configure PostgreSQL and Drizzle

Use this layout:

```text
server/
  drizzle.config.ts
  drizzle/
  src/
    db/
      client.ts
      schema.ts
```

Use `server/src/db/schema.ts` as the source of truth. Point Drizzle Kit to it and output generated migrations to `server/drizzle/`.

Generate and apply migrations from the workspace root:

```powershell
pnpm --dir server db:generate
pnpm --dir server db:migrate
```

Inspect generated SQL before applying it. Never use `db:push` as the shared or production migration path. Add Docker-managed PostgreSQL only when requested.

## 5. Configure environment files

Commit placeholder samples and keep working values uncommitted.

Server sample:

```dotenv
PORT=3001
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/app_name
DASHBOARD_ORIGIN=http://localhost:3000
SESSION_SECRET=replace-with-a-long-random-secret
```

Client sample for an authenticated same-origin proxy:

```dotenv
API_INTERNAL_BASE_URL=http://localhost:3001
SESSION_COOKIE_NAME=<project-session-cookie>
```

Keep both client values server-only. Do not add `NEXT_PUBLIC_API_BASE_URL` unless the browser must call an explicitly public API directly. Add provider variables only with their integration.

## 6. Add the authenticated proxy

When authentication is selected, create `client/app/api/backend/[...path]/route.ts` and preserve this flow:

```text
browser -> /api/backend/* -> read HttpOnly cookie -> Authorization: Bearer <token> -> Hono /v1/*
```

Forward only allowed methods, headers, query parameters, and bodies. Do not forward hop-by-hop headers. Handle login/logout token-to-cookie behavior explicitly and never return the bearer token to browser JavaScript.

Use one configured cookie name. Set HttpOnly, SameSite, Secure in production, path, and expiry deliberately. Return stable proxy errors when the server is unavailable or produces an invalid response.

## 7. Add application conventions

Merge the approved conventions into the existing root `AGENTS.md`; do not replace its workspace instructions. Keep feature code shaped as:

```text
client/features/<feature>/
  components/
  hooks/
  model.ts
  service.ts

server/src/modules/<feature>/
  model.ts
  service.ts
  controller.ts
  routes.ts
```

Do not generate placeholder business modules. Add the first real feature through the full flow only when requested.

Client rules:

- prefer Server Components and add `"use client"` only for browser APIs, event handlers, or client state;
- keep App Router pages thin and feature-specific code together;
- call protected APIs through feature services and the shared `dashboardApi`;
- keep request/response types explicit;
- promote UI to `components/ui` only after a second consumer;
- apply `vercel-react-best-practices` when available.

Server rules:

- preserve `routes -> middleware -> controller -> service -> Drizzle/integration`;
- validate untrusted input at the HTTP boundary;
- keep controllers limited to HTTP parsing and response mapping;
- keep business rules, authorization, ownership, and transactions in services;
- use centralized environment access, response envelopes, errors, logging, and the shared Drizzle client;
- change schema, generated migration, and affected contracts together.

## 8. Configure optional R2

Only when selected:

```powershell
pnpm --dir server add @aws-sdk/client-s3
```

Add server-only placeholders:

```dotenv
R2_ACCOUNT_ID=
R2_ACCESS_KEY_ID=
R2_SECRET_ACCESS_KEY=
R2_BUCKET=
R2_PUBLIC_URL=https://assets.example.com
```

Keep one adapter at `server/src/integrations/r2/r2.ts`. Let feature services own validation, key policy, authorization, persistence, and compensating deletion.

## 9. Format and verification handoff

After the approved setup is complete, use the existing workspace formatter:

```powershell
pnpm format
```

If repository instructions prohibit a mutating formatter, provide the command and report that it was not run.

When verification execution is allowed, use only scripts present in the generated manifests:

```powershell
pnpm format:check
pnpm typecheck
pnpm lint
pnpm test
pnpm build
```

For runtime verification, start both applications separately and confirm the health endpoint, dashboard, proxy boundary, migrations, secrets boundary, and single root lockfile. Report formatting, static checks, builds, and runtime flows separately.
