## 1. Inspect the bootstrap

Require these existing paths:

```text
package.json
pnpm-workspace.yaml
client/package.json
server/package.json
.agents/skills/sk-start-next-hono/SKILL.md
```

If any are missing, stop and tell the user to create the base project first:

```powershell
npx sb-kit create next-hono <project-name>
```

Read the root and child manifests, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `.prettierrc.json`, `.prettierignore`, root `AGENTS.md`, and generated entry points. A non-empty matching workspace is expected. Preserve the generated applications and do not rerun create-next-app or create-hono.

Confirm only one root pnpm lockfile exists. Report child npm, Yarn, or Bun lockfiles instead of silently changing unrelated user files before approval.

## 2. Confirm current tooling

Inspect the versions already selected by the generated manifests and lockfile. Preserve them unless the approved setup needs a change; report known affected versions instead of silently upgrading unrelated dependencies.

### Dependency security selection

Before selecting or changing dependency versions:

1. Consult the framework/vendor security advisories and official release notes for the selected supported major/minor line. Use public registry metadata to confirm publication, Node engine requirements and peer compatibility (including matching React/React DOM versions); registry existence or satisfying a peer range does not prove security.
2. Choose a published version covering the relevant known advisories. Do not copy a remembered old pin or hardcode an advisory's patched version as permanently current. Prefer an exact pin for a reproducible source-only handoff, or a range whose minimum version is at least the applicable verified patched floor. For example, a broad caret range starting below that floor is not repaired just because it *can* resolve a safe version.
3. Inspect an existing lockfile separately: a safe manifest floor does not prove the lockfile resolves safe versions. Propose any necessary manifest/lockfile update for approval and perform package operations only when permitted. Keep one pnpm lockfile; never fabricate a resolved lockfile when installation is prohibited.
4. Record selected versions, advisory/release URLs, lookup date, peer/engine evidence, and what remains unresolved. If research is unavailable, report that uncertainty; do not claim security readiness, invent a latest version, or silently pick a known affected range. Runtime compatibility, installed/transitive dependency security, and successful compilation remain unverified until separately permitted checks are run.

Confirm the backend runtime before planning: Node.js (default) or Cloudflare Workers. Honor an explicit user choice and preserve an existing runtime adaptation unless a change is approved. Confirm authentication and optional Cloudflare R2. PostgreSQL with Drizzle is the default data layer; authentication defaults to an admin/user boundary; R2 defaults to omitted.

For Workers, read [cloudflare-workers.md](cloudflare-workers.md) and include the in-place runtime conversion in the approved plan. Its instructions replace the Node-specific portions of sections 3, 4, 5, and 8 below. Common workspace, proxy, migration, module, and permission rules still apply. Do not rerun create-hono or silently provision cloud resources.

Use the root scripts already generated by the CLI:

```json
{
  "scripts": {
    "dev:client": "pnpm --dir client dev",
    "dev:server": "pnpm --dir server dev",
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

Do not add sb-kit as a dependency or rerun its installer.

## 3. Configure the server

For a Node.js backend, reuse the valid scripts and dependencies created by the Hono Node.js template. For Workers, use the Workers reference instead of adding the Node driver, adapter, listener, or signal handlers below. Add only missing baseline dependencies:

```powershell
pnpm --dir server add drizzle-orm postgres zod
pnpm --dir server add -D drizzle-kit
```

Use `zod` or an existing validated-schema dependency; never add two validation libraries.

Keep one development command and one production entry point. Add only missing scripts supported by the generated toolchain:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "db:generate": "drizzle-kit generate",
    "db:migrate": "drizzle-kit migrate"
  }
}
```

Compose `server/src/index.ts` to:

- use `@hono/node-server`;
- use port `3001` by default;
- mount API routes beneath `/v1`;
- expose `GET /v1/health`;
- allow the exact `DASHBOARD_ORIGIN` in CORS;
- apply structured request logging and secure headers;
- use a global error handler;
- close the HTTP server on `SIGINT` and `SIGTERM`.

## 4. Configure PostgreSQL and Drizzle

Use this layout:

```text
server/
  drizzle.config.ts
  drizzle/
  src/
    db/
      client.ts
      schema.ts
```

Use `server/src/db/schema.ts` as the source of truth. Point Drizzle Kit to it and output generated migrations to `server/drizzle/`. For Node.js, keep the shared Drizzle client in `src/db/client.ts`; for Workers, use a request-scoped factory with explicit cleanup as described in the Workers reference. Preserve existing schemas and migration history.

Load the migration-only `DATABASE_URL` explicitly in the Drizzle Kit config from the environment or an untracked local file. Drizzle Kit runs in local Node.js tooling/CI, not in the Worker. Do not read Worker bindings from migration configuration or run migrations inside request handlers.

Generate and apply migrations from the workspace root:

```powershell
pnpm --dir server db:generate
pnpm --dir server db:migrate
```

Inspect generated SQL before applying it. Never use `db:push` as the shared or production migration path. Add Docker-managed PostgreSQL only when requested.

## 5. Configure environment files

Commit placeholder samples and keep working values uncommitted.

Node.js server sample (Workers uses bindings and local `.dev.vars` as described in its reference):

```dotenv
PORT=3001
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/app_name
DASHBOARD_ORIGIN=http://localhost:3000
SESSION_SECRET=replace-with-a-long-random-secret
```

Client sample for an authenticated same-origin proxy:

```dotenv
API_INTERNAL_BASE_URL=http://localhost:3001
SESSION_COOKIE_NAME=<project-session-cookie>
APP_ORIGIN=http://localhost:3000
```

Keep all three client settings server-only. Validate `APP_ORIGIN` as an exact HTTP(S) origin (scheme, hostname, optional port; no credentials/path/query/fragment/trailing slash), use HTTPS in production, and align it with the Hono `DASHBOARD_ORIGIN`. Configure preview/staging/production origins explicitly; do not derive the trusted origin from the incoming request. Use local API port `3001` for either runtime; Workers must set it in Wrangler's dev configuration. In production, point `API_INTERNAL_BASE_URL` to the deployed API origin, including an HTTPS Worker origin when selected, and preserve the existing `/v1` mapping. Do not add `NEXT_PUBLIC_API_BASE_URL` unless the browser must call an explicitly public API directly. Add provider variables only with their integration.

## 6. Add the authenticated proxy

When authentication is selected, read [authenticated-proxy.md](authenticated-proxy.md) in full and adapt its complete Route Handler, shared helpers, browser transport and Hono guard composition. Then create `client/app/api/backend/[...path]/route.ts` and preserve this flow:

```text
browser -> /api/backend/* -> validate write Origin -> read HttpOnly cookie -> Authorization: Bearer <token> -> Hono /v1/*
```

Forward only allowed methods, headers, query parameters, and bodies. Do not forward hop-by-hop headers. Handle login/logout token-to-cookie behavior explicitly and never return the bearer token to browser JavaScript.

Use one configured cookie name. Set HttpOnly, SameSite, Secure in production, path, and expiry deliberately. Cookie settings do not replace the Origin guard. If verification/login/session issuance is explicitly deferred, deny protected access at a **mounted Hono auth guard**, not by omitting the Next.js transport. The proxy returns 401 locally for a missing cookie, but with a cookie it must still perform path/query/header/body forwarding and response validation; Hono denies the unverified token. Do not invent token issuance or treat any cookie/bearer contents as identity. A constant 401, unused API URL, or client-only response validator is incomplete setup unless the user explicitly approves a disabled transport and it is reported as partial.

### Origin guard before cookie access

This Route Handler is a cookie-authenticated browser boundary, not a Next.js Server Action; do not assume Server Action origin protections apply to it. On POST/PUT/PATCH/DELETE (and any other allowed unsafe method), require an `Origin` header exactly equal to validated server-only `APP_ORIGIN`. Reject missing, `null`, malformed, multiple, or mismatched values with `403 origin_not_allowed` before calling `cookies()`, constructing Authorization, reading a write body, or fetching Hono. Validate trusted configuration first and return `503 proxy_not_configured` when it is missing/invalid.

Insert this guard inside the proxy after configuration validation and before cookie access; `NextResponse` comes from `next/server`:

```ts
const safeMethods = new Set(["GET", "HEAD", "OPTIONS"]);
if (!safeMethods.has(request.method) && request.headers.get("origin") !== appOrigin) {
  return NextResponse.json(
    { success: false, error: "origin_not_allowed" },
    { status: 403, headers: { "Cache-Control": "no-store" } },
  );
}
// Only now read the configured HttpOnly cookie and construct the bearer header.
```

The method allowlist runs first. OPTIONS, when exposed, is a local non-mutating preflight and must not read a session or forward an authenticated write. GET/HEAD must never change application state. Do not trust `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `Referer` fallback, or `request.nextUrl.origin` to define the approved public origin. Reverse proxies must preserve the browser Origin; named preview origins need explicit trusted configuration, not a wildcard.

Forward only the successfully validated write Origin to Hono as defense in depth. Checking only Hono's Origin/CORS is insufficient: the Next.js proxy creates a new request and may omit the browser Origin. CORS controls browser response access, not identity or general CSRF protection. Origin headers can be forged by non-browser clients, so Hono still must verify bearer tokens and enforce authorization. Server-to-server clients should normally call Hono directly with verified credentials rather than bypassing the cookie proxy guard.

### Backend response validation

Define one response schema shared by the API and proxy. The baseline is `{ success: true, data: ... }` for contentful successful 2xx responses and `{ success: false, error: "non-empty-code" }` for 4xx/5xx responses. Preserve an existing structured error contract only when explicitly inspected; then validate its required fields consistently in Hono, proxy and client instead of silently changing it to a string.

For the baseline, this predicate checks shape and status agreement (not feature-specific DTO validation):

```ts
function isApiEnvelope(value: unknown, ok: boolean): boolean {
  if (typeof value !== "object" || value === null || Array.isArray(value)) return false;
  const envelope = value as Record<string, unknown>;
  return ok
    ? envelope.success === true && Object.prototype.hasOwnProperty.call(envelope, "data")
    : envelope.success === false && typeof envelope.error === "string" && envelope.error.trim().length > 0;
}
```

Apply the response pipeline in this order:

1. Fetch using `redirect: "manual"` and `cache: "no-store"`. Reject unsupported statuses and redirects as `502 invalid_backend_response`; do not follow a login/error redirect and mistake an HTML page for API success.
2. Handle HEAD and 204/205 explicitly with a null body and no JSON parsing. A HEAD response may preserve a valid upstream success/error status without a body. Exclude redirects/unsupported statuses first. No-content responses are deliberate exceptions to the envelope contract, not malformed JSON.
3. For other responses, parse the Content-Type media type exactly (ignore parameters/case); require `application/json` for this baseline. Add another JSON media type only as an explicit API contract decision, not via a substring match.
4. Parse the body as `unknown` and validate the envelope plus HTTP status: contentful 2xx requires `success: true` and an own `data` property; 4xx/5xx requires the agreed error shape and `success: false`. Reject arrays, primitives, null, `{}`, malformed JSON and status/envelope mismatches. Parsing JSON or casting `as T` is not validation.
5. Return valid payloads with their upstream status. Return a stable JSON `502 invalid_backend_response` for media/parse/contract failures without reflecting raw upstream content; distinguish transport failure as `502 backend_unavailable`. Release discarded response bodies and do not let discard/cleanup failure change the intended error classification.
6. Set `Cache-Control: no-store` on all proxy responses, including local errors. Do not forward upstream cookies, redirect locations, hop-by-hop headers or public caching directives. A valid error envelope preserves the API status rather than being rewritten as generic success.

Keep no-body semantics on locally generated HEAD errors too. In `client/lib/api/client.ts`, check a no-body response's `response.ok` before returning an empty result: HEAD 401/403/500 must throw an API error, while a successful HEAD/204/205 can resolve explicit `undefined`. Use the complete [browser transport example](authenticated-proxy.md#browser-transport-and-head-errors), not an early HEAD return that hides HTTP failures. A JSON-only proxy is not a streaming/download proxy; design and approve those routes separately. Implement login/logout token-to-cookie mapping explicitly rather than forwarding token-bearing authentication responses as ordinary JSON.

## 7. Add application conventions

Merge the approved conventions into the existing root `AGENTS.md`; do not replace its workspace instructions. Keep feature code shaped as:

```text
client/features/<feature>/
  components/
  hooks/
  model.ts
  service.ts

server/src/modules/<feature>/
  model.ts
  service.ts
  controller.ts
  routes.ts
```

Do not generate placeholder business modules. Add the first real feature through the full flow only when requested.

Client rules:

- prefer Server Components and add `"use client"` only for browser APIs, event handlers, or client state;
- keep App Router pages thin and feature-specific code together;
- call protected APIs through feature services and the shared `dashboardApi`;
- keep request/response types explicit;
- promote UI to `components/ui` only after a second consumer;
- apply `vercel-react-best-practices` when available.

Server rules:

- preserve `routes -> middleware -> controller -> service -> Drizzle/integration`;
- validate untrusted input at the HTTP boundary;
- keep controllers limited to HTTP parsing and response mapping;
- keep business rules, authorization, ownership, and transactions in services;
- use centralized environment access, response envelopes, errors, logging, and the Drizzle client/factory appropriate to the selected runtime;
- on Workers, pass request-scoped dependencies into services instead of passing Hono context or caching live connections globally;
- change schema, generated migration, and affected contracts together.

### Source-review and regression checklist

Read the implementation path for every relevant case below before handoff. Add tests only within approved scope and execute them only when permitted; otherwise list these scenarios for the user and mark them Not run.

| Area | Cases and expected boundary |
| --- | --- |
| Dependencies | Existing resolved versions versus manifest constraints; selected pins/range floors cover cited advisories; React peers/Node engines compatible; no fabricated lockfile or safe-version claims without evidence |
| Completeness | Actual cookie-to-bearer fetch, /v1 mapping and query/header/body forwarding; mounted Hono guard denies while verification is deferred; constant 401/no fetch/client-only validation is not complete |
| Origin | Allowed write Origin reaches cookie lookup; missing/null/wrong/malformed Origin returns 403 before cookie/body/backend access; spoofed Host/forwarded headers cannot change approval |
| Read/preflight | GET/HEAD have no state changes; allowed OPTIONS is local and non-authenticated; denied methods do not reach Hono |
| JSON contract | Valid success and error preserve status; HTML, broken JSON, null/array/primitive/empty object and success/status mismatch return stable 502 |
| No-content | HEAD, including local failures, and 204/205 have no body or JSON parsing; client throws on HEAD 401/403/500 instead of returning undefined; redirects are not accepted as API success |
| Transport/cache | Network failure is distinct from invalid response; discarded-body cleanup does not overwrite the intended error; all proxy paths are no-store with no token/cookie leakage |
| Database | Connect failure still attempts cleanup; operation failure closes client; operation+cleanup failure preserves the original thrown value, even if falsy; cleanup-only failure is surfaced; see the Workers lifecycle example |

For runtime verification, start both applications separately and confirm the health endpoint, dashboard, proxy boundary, migrations, secrets boundary, and single root lockfile. Report formatting, static checks, builds, and runtime flows separately. A dry-run bundle does not prove database, bindings, auth, or deployed behavior. Deploying or provisioning resources is not an implicit verification step and requires explicit authorization.
